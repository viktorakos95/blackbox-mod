## Fourth round (image n12)
- [x] **7. USB MIDI (the important one)** [n12]. What the path is, from the code:
  - The Blackbox's USB-A port is the OTG_FS controller in HOST mode: the vector for IRQ 101 is `HAL_HCD_IRQHandler` (0x0807b650, it tests the host mode and the HCINT / HPRTINT bits); the OTG_HS vector (77) is an empty stub. The host thread is `USBH_Thread` (0x08089b58) and the stock MIDI host class driver is app code at 0x08046630 (it asks `FindInterface(class 1, subclass 3)` and starts receive transfers of 0x200 bytes).
  - Each completed receive calls the app callback at 0x08044f1c, which copies the 512-byte buffer (4-byte USB-MIDI event packets, the code index in the low nibble of byte 0, a 0 ends them) into the stock slot ring with 0x080446da (4 slots of 0x300 at mgr + 0x5070). The render (0x0804cb4e -> 0x08044844 -> 0x08044708) turns the slots into 5-byte messages (status, d1, d2, -, length) in the software queue (mgr + 0x4660, read index 0x4b60, write index 0x4b64), and the poll 0x0804495e returns them after the jack's ring (the flag byte is 1 then, 0 for the jack). That software queue is where MCL's port 2 takes them (`mcl_softq_take` inside the poll), so MCL and DRONE-8 read the same place, the poll.
  - **Why n10 did not work:** I thought clkmon already hooked the USB callback; its patch no longer does (removed earlier, `patches/clkmon.py`), so the interrupt-side part never ran. And the poll hook alone did not deliver USB to DRONE-8 on the unit. I could not find the reason by reading the code (the queue path is the one MCL uses), so n12 does not trust it:
  - **n12:** (a) a hook on the callback's copy (patches/lira.py, `bl 0x080446da` at 0x08044f2c -> `lira_usb_rx`): counts every packet, queues controller changes and notes into a small ring (interrupt safe, only when the backup SRAM is on), then calls the stock copy unchanged; the audio task drains the ring in the poll hook. (b) The poll hook still handles jack messages (flag 0) and counts queue messages; it acts on queue messages only while the callback hook has never seen a packet (otherwise a note would press twice). (c) Switch: `lira_usb_hook` (const, 1 in the image; 0 leaves the callback to the stock code). (d) The MIDI panel's fourth cell on the ENV tab shows `IN`, `J<n>` (messages from the jack), `U<n> C<n>` (U: from USB through the queue or the ring, C: raw USB packets in the callback), counted since boot, capped at 999. On the unit: plug the device in, move something: if C counts up, the callback path works; if U counts but C stays 0, only the queue sees it.
  - Emulator: the callback hook with a buffer of packets (counts, ring, stock copy called with the same buffer, only CC / notes taken, switch off), the poll with the flag. NOT verified on the unit: the whole thing (no USB device in the emulator).
